# DeckVerse V1.2 full QA and stability audit

Audit date: 2026-10-20 (Asia/Calcutta)  
Production: https://addictive-themed-card-games.vercel.app  
Baseline: `main` at `f9845a847a45900182d7d9f53df6d80d5c4131fc`  
Audit branch: `codex/deckverse-v1-2-qa`

## Executive verdict

**NO-GO for an unrestricted public/competitive launch.** The core two-player engine, authoritative multiplayer transactions, reveal synchronization, privacy boundaries, and synthetic LiveKit media path are sound. A limited beta is technically supportable. Public release should wait for physical iOS/Android media testing, abuse throttling, host-loss/presence recovery, a decision on the measured first-chooser advantage, and resolution of Pokémon name/art licensing.

No P0 defect was found. The branch contains minimal P2 fixes for strict API validation, keyboard focus/touch targets, PWA cache completeness, and stale deployment documentation. No database, Vercel variable, LiveKit credential, deployment, or unrelated application was changed.

## Scope and evidence

- Repository architecture, engine, API, PWA cache, CI history, docs and dependency graph inspected.
- Supabase contract was read first. Only `hub` registration and `deckverse.*` metadata/data counts were queried read-only.
- Production API exercised with isolated QA rooms; every created room was closed in cleanup.
- Production Chrome and Edge covered at 320×568, 360×800, 390×844, 430×932, 768×1024, 1024×768, 1366×768 and 1920×1080.
- Two independent production browser sessions exercised create/join/ready/start/reveal. Real LiveKit Cloud was exercised with synthetic microphone/camera devices.
- Physical iOS Safari, Android Chrome, real microphones/cameras, backgrounding and actual network loss were not available and are explicitly unverified.

## Game logic and balance

- 16 unit tests pass after fixes (14 baseline tests plus 2 validation tests).
- The 50-card two-player deck contains unique valid cards and deals 25/25.
- Rank correctly treats lower as better; all other categories treat higher as better.
- Winner collection order, tie pot, chooser retention on the first tie, chooser switch on the second consecutive tie, rank sudden-death, hidden rival top card and conservation across 1,000 turns pass.
- All 1,225 card pairs × 8 stats (9,800 comparisons) show zero complete-dominance and zero dominance relationships. Per-card comparison rates range from 0.4898 to 0.5089.
- Ten-thousand-match simulation: 0 stalls, first chooser 59.2%, median 57 rounds, p90 149, p99 283. The engine terminates, but competitive fairness needs product review.

## Multiplayer and race behavior

Production full-flow timings: create 357 ms, join 141 ms, ready 145 ms, confirm-ready 104 ms, total scripted flow 4,022 ms. Server-authoritative concealment, host-only settings, snapshot reveal policy, both-card reveal, blocked early selection, two-party manual acknowledgement, and next-round policy all passed.

Concurrent requests are serialized by the room row lock:

- Two simultaneous joins: statuses 200 and 400; exactly one guest obtained the seat.
- Two simultaneous round-0 selections: statuses 200 and 409; the round advanced once.
- Invalid session token: 401.

Controlled active-room cohorts produced no errors:

## Reveal and LiveKit report

- Automatic 2/3/5/8-second policy validation and manual two-ack/90-second fallback pass unit and production integration tests.
- An in-progress reveal keeps its snapshotted policy when the host changes future settings.
- Only the host can change settings; a guest receives 403.
- LiveKit token issuance checks active membership, remote mode and active match, and grants only the UUID-derived room for two hours. No credential is returned by the configuration probe.
- Two independent Chrome sessions connected to real LiveKit Cloud with fake media; microphone toggle, camera publication, opponent subscription in both directions, and leaving the call without disrupting card play passed.
- Remaining field matrix: physical iPhone Safari, Android Chrome, real permission denial, audio autoplay, device switching, background/resume, packet loss and reconnect.

## Responsive, accessibility and visual report

- Chrome and Edge passed all eight requested viewport sizes with landing, setup and practice battle rendered, both cards visible, no actionable horizontal scroll and no page errors.
- Deliberately oversized ambient decoration increases raw paint bounds by 240 px on ≥768 px layouts but is clipped and does not create a user-scrollable overflow.
- Reduced-motion CSS is present. Semantic buttons/inputs and accessible labels exist for icon-only call controls.
- The branch raises battle controls to 44 px and adds a consistent visible keyboard focus outline.
- Remaining accessibility work: automated axe/assistive-technology coverage, 200% zoom matrix, real touch/virtual keyboard testing, and richer form-error associations.

Screenshot evidence is in `artifacts/qa/screenshots/production-chrome/` and `artifacts/qa/screenshots/production-edge/`.

## Performance report

- First-party static payload decoded by the browser was approximately 86.9 KB on production (excluding remote fonts/artwork); local branch was approximately 89.3 KB.
- Key source sizes: HTML 13.9 KB, CSS 32.0 KB, app JS 20.4 KB, catalog 12.7 KB, LiveKit adapter 7.9 KB, engine 4.9 KB.
- Production DOMContentLoaded across the sampled Chrome runs ranged from 587 to 1,632 ms; full scripted landing→setup→battle flows ranged from 2.5 to 4.7 seconds and include remote Pokémon image/network idle waits.
- Static HTML was served from Vercel cache with HSTS. API health used `no-store`, `nosniff`, and a cache miss as expected.
- No critical bundle-size regression was introduced. Runtime LiveKit CDN loading and numerous remote card images remain the main external performance dependencies.

## Security and Supabase report

- `npm audit --omit=dev`: zero known vulnerabilities across six production dependencies.
- No committed database or LiveKit secret was found in the reviewed source. Browser storage contains nickname and opaque per-room session token, not database credentials.
- API request bodies are size-bounded; actions, codes and tokens are allowlisted/validated; tokens are stored hashed; room mutation is row-locked; errors avoid raw database details.
- Dynamic player/card text is escaped before HTML insertion. The remaining inline image `onerror` handler complicates a strict CSP and should be replaced before CSP rollout.
- Supabase app #16 is registered as slug/schema `deckverse`. Only `deckverse.rooms`, `deckverse.players`, the schema and the DeckVerse LiveKit external service are registered resources.
- RLS is enabled on both tables. Policies and CRUD grants are limited to `deckverse_app`; anon/authenticated roles have no table access. Current Supabase security and performance advisors reported zero findings scoped to `deckverse`.
- Counts at audit time were 57 rooms and 113 player rows; relation sizes were approximately 106 KB and 196 KB. No database mutation was made by the schema audit.

3. P1: define and implement heartbeat, disconnect grace, host transfer/forfeit and abandoned-room cleanup.
4. P1: complete the physical iPhone/Android LiveKit matrix and credential rotation follow-up.
5. P1: resolve Pokémon IP licensing before unrestricted commercial launch.

8. P2: add axe, 200% zoom, offline/reconnect and long-session browser automation.

## Release recommendation

Proceed only as a monitored limited beta with clear support expectations. Do not declare unrestricted production readiness until DV-01 through DV-05 are resolved or explicitly accepted by accountable product/security/legal owners.
